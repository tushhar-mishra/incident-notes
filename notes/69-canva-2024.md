## ⚡ Core: the 10-minute version

**The idea.** At 08:47 UTC Canva deployed a new version of its editor. Browsers began downloading the new JavaScript files. One path through Cloudflare (Singapore ↔ Ashburn) was suffering heavy packet loss, so **one file** (the object panel) took **20 minutes** to download. Cloudflare merged all requests for that file into **one** stream, so **270,000+** users (mostly in Southeast Asia) waited on it — with **no errors**. At 09:07 the file arrived for all of them **at the same instant**, and every browser fired its next API calls together: about **1.5 million requests per second**, three times normal peak. The API Gateway collapsed.

```
08:47 deploy → new JS assets → one asset stuck 20 min (SIN–IAD path packet loss up to ~66%)
      CDN request coalescing: 270,000+ requests wait on ONE stream (no errors → canary sees nothing)
09:07 asset completes for everyone at once → ~1.5M req/s to API Gateway (3× peak)
      gateway throughput already reduced by a telemetry lock-contention bug
      → memory grows → OOM killer kills all gateway containers within ~2 min
      → new tasks: healthy → instantly flooded → killed again
09:08 canva.com unavailable · 09:29 block ALL traffic at the CDN → tasks recover
      → redirect to status page → restore traffic gradually (Australia first, strict rate limits) → ~10:00
```

**Picture it.** A shop door gets stuck for 20 minutes while thousands of people queue outside quietly. Then the door suddenly opens and everyone rushes in at once. The shop, which can comfortably serve a steady crowd, is crushed — and every time new staff arrive, the crowd knocks them over too, until the manager locks the doors and lets people in a few at a time.

**The one thing to know.** **Waiting is load that hasn't arrived yet.** Anything that makes many clients wait together (coalescing, locks, slow dependencies) will release them **together**. Use **timeouts**, **load shedding**, and recovery by **gradual admission**.

**You've got it if you can:** explain why the canary didn't catch the bad deploy and why scaling up didn't help.

## Summary

On 12 November 2024, a slow network path inside Cloudflare delayed one of the JavaScript assets for a new Canva editor release for 20 minutes. Request coalescing at the CDN held more than 270,000 user requests on a single stream; when the asset finished, they all proceeded at once, sending about 1.5 million requests per second to Canva's API Gateway — three times typical peak. The gateway, whose throughput was already reduced by a telemetry library bug, ran out of memory and all its tasks were killed; Canva blocked traffic at the CDN, recovered capacity, and readmitted users gradually. canva.com was unavailable from 09:08 to about 10:00 UTC.

| Item | Detail (from Canva's incident report) |

| Load | ~**1.5 million requests/second** to the API Gateway, about **3× typical peak** |

## How it happened

```
Browser ──► Cloudflare (CDN) ──► origin (S3) for new JS assets
              │  IPv6 traffic between Ashburn and Singapore sent over public transit
              │  (stale traffic-management rule) → packet loss ~66% at peak
              │  Concurrent Streaming Acceleration: one upstream fetch, many waiting clients
              ▼
   270,000+ clients wait (no error, no timeout) ... 20 minutes ... asset done
              ▼
   all clients load the object panel at once → API calls → API Gateway (Netty, event loop)
              │  telemetry library regression: re-registers metrics on every value under a LOCK
              │  → lock contention → much lower max throughput per task
              ▼
   load balancers keep opening connections to overloaded tasks → off-heap memory grows → OOM
   → all tasks killed in ~2 min → replacements marked healthy → immediately flooded → killed
```

Cloudflare's statement (quoted in Canva's report) attributes the path problem to "a stale rule in Cloudflare's traffic management system"; Cloudflare says it removed the rule. Canva notes the telemetry fix had entered its release process that same day, but they "underestimated the impact of the bug and didn't expedite deploying the fix."

## Why it spread

- **Synchronised clients:** coalescing turned a slow trickle into one huge burst.
- **Canary blind spot:** the canary aborts on rising **errors**, but "no errors were recorded because requests didn't complete."
- **Reduced headroom:** the lock-contention bug lowered per-task capacity.
- **Load balancers fed the fire:** new connections went to already overloaded tasks.
- **Autoscaling outpaced:** OOM kills were faster than scaling; manually raising the desired count "didn't mitigate the issue" because each new task was killed by the ongoing spike.

## How they found it

Canva's report does **not** describe how the incident was first detected (**not publicly disclosed**). It explains that the deploy canary did not flag the release because requests were stalled, not failing.

## What they did to fix it

1. Raised the desired gateway task count (didn't help on its own).
2. **Blocked all traffic at the CDN** with a temporary Cloudflare firewall rule (09:29), so new gateway tasks could start without being overwhelmed.
3. Redirected canva.com to the **status page**.
4. Once healthy task counts were stable, **restored traffic incrementally**, starting with **Australian users under strict rate limits**.

## Permanent fix (as listed by Canva)

| Change | Pattern it addresses |
|---|---|
| Runbook for granular **rerouting, blocking and progressive scale-up** of traffic | Recovery by gradual admission |
| More informative error page when canva.com is unavailable | Communication |
| **Increased baseline task count and per-task memory** (done) | Headroom |
| **Load-shedding rules** in the API Gateway | Overload protection |
| **Regular load testing** of the gateway | Know your limits |
| Patch for the telemetry thread-locking bug (deployed); multithreaded microbenchmarks | Throughput regression |
| **Page-load completion events** as a secondary canary signal; an extra rollout stage | Canary blind spot |
| **Timeouts for asset fetches** so requests don't wait excessively on coalesced requests | Unbounded waiting |

## In my stack

| Same risk in my tools | How I'd prevent it |
|---|---|
| Nginx `proxy_cache_lock` / CDN request collapsing without a timeout | Set lock timeouts (`proxy_cache_lock_timeout`) so waiters fall through gradually |
| Canary analysis only on error rate | Also on latency, request completion, saturation ([SD 34](../../System-Design/notes/34-deployment-strategies.md)) |
| Gateway pods (Kubernetes) restarted into full traffic | Readiness gates + slow start (e.g. Envoy slow-start mode, ALB slow start), admission control |
| HPA can't react to a spike that kills pods in seconds | Load shedding inside the service; baseline headroom; rate limits at the edge ([K8s 48](../../CKA-Certification-Course-2025/notes/48-metrics-server-and-hpa.md)) |
| A known performance bug waiting in the release queue | Assess impact of known throughput regressions; expedite fixes on critical paths |
| Recovering after an overload | Block at the edge, then readmit by region/percentage (topic 37) |

## Follow-up questions

1. **Q: What was the real root cause?**
   A: Unbounded waiting at the CDN (coalescing with no effective timeout) turned a 20-minute slow asset into a synchronized burst, hitting an API Gateway with reduced capacity from a lock-contention bug and no load shedding. The network path problem and the deploy were triggers.

2. **Q: Why didn't the canary catch it?**
   A: It looked for errors; stalled requests produced none. Canva added page-load completion events as a canary signal.

3. **Q: What would you check first?**
   A: The gateway's request rate vs normal (3× peak means a herd), whether tasks are being OOM-killed, and what changed (the deploy, CDN behaviour).

4. **Q: How did they stop the impact?**
   A: Blocked all traffic at the CDN so the gateway could recover, then readmitted traffic gradually with rate limits.

5. **Q: Why didn't scaling up help?**
   A: Each new task became healthy and was immediately hit by the full spike, then killed. Capacity can't be added faster than an unbounded herd destroys it; you must cut the load first.

6. **Q: What changed permanently?**
   A: More headroom, load shedding, load testing, the telemetry fix, better canary signals, asset-fetch timeouts, and a traffic-control runbook.

7. **Q: How would you confirm the fixes?**
   A: Load-test the gateway at 3× peak and confirm it sheds load and stays up; simulate a stalled asset and confirm requests time out gradually.

8. **Q: What if blocking at the CDN hadn't been possible?**
   A: Use the gateway's own rate limiting/load shedding, scale behind a closed door (stop LB health checks marking tasks ready until enough exist), or shed at DNS. That's why the runbook matters.

9. **Q: How would you prevent this class of incident?**
   A: Timeouts on every wait, load shedding at every entry point, and recovery by staged admission.

10. **Q: What would you do differently with the known telemetry bug?**
    A: Measure its throughput impact and expedite it; a "minor" performance bug on a critical path can be the difference between surviving a spike and collapsing.
