## ⚡ Core: the 10-minute version

**The idea.** Fastly is a CDN (Content Delivery Network) used by many large websites. On 12 May 2021 it deployed software that contained a bug. Nothing happened for almost four weeks. On 8 June, one customer pushed a **perfectly valid** configuration change that happened to hit the exact conditions for the bug. **85% of Fastly's network started returning errors**, and many big websites appeared "down" at once.

```
May 12   software deploy → latent bug (needs a specific config + specific circumstances)
Jun 8    09:47 customer pushes valid config → bug triggers → 85% of network returns errors
         09:48 Fastly monitoring detects it (1 minute)
         10:27 engineers identify the customer configuration → disable it
         10:36 services start recovering; within 49 minutes 95% of network normal
         17:25 permanent bug fix begins deploying
```

**Picture it.** A new lock is installed in every apartment in a city. It works fine for a month. Then one resident sets an unusual but allowed combination, and a flaw in the lock design jams the doors of most buildings in the city.

**The one thing to know.** **Testing can't find every input combination.** What saves you is **fast detection**, a **fast way to disable the trigger**, and designs where one tenant's config **can't** take down everyone (isolation).

**You've got it if you can:** explain why the root cause was the May bug, not the June customer, and why "a valid config" matters.

## Summary

On 8 June 2021, Fastly suffered a global outage caused by an undiscovered software bug that had been introduced in a 12 May software deployment. A valid customer configuration change triggered the bug under specific circumstances, causing 85% of Fastly's network to return errors. Fastly detected it within a minute, disabled the configuration, and had 95% of the network operating normally within 49 minutes.

## How it happened

```
          ┌──── May 12 deploy: bug present on (nearly) every node, dormant ────┐
          │                                                                     │
Customer ─┤ Jun 8: pushes a VALID config change containing the "specific       │
          │        circumstances"                                               │
          └─────────────► config distributed across the network ──────────────►│
                                                                                ▼
                                   bug triggers on nodes processing it → errors on 85% of network
```

What Fastly **did not** publish: what the bug was, what the "specific circumstances" were, which customer, and why testing missed it (Fastly said it would find out why QA didn't detect it). These are **not publicly disclosed**.

## Why it spread

- **Shared platform:** all customers share the same software on the same nodes, so one customer's config affected others.
- **Config distributed widely and quickly** (the general pattern of topic 24).
- **The bug was everywhere already** (deployed on 12 May) — redundancy didn't help because every node had the same flaw.

## How they found it

- **Fastly's own monitoring** identified the global disruption at 09:48, one minute after onset.
- Engineers then needed **40 minutes** (09:48 → 10:27) to identify the **customer configuration** responsible. Fastly doesn't describe the investigation steps (**not publicly disclosed**).

## What they did to fix it

1. **Isolated and disabled the customer configuration** that triggered the bug.
2. Services recovered from 10:36; 95% of network normal within 49 minutes.
3. Created a **permanent fix** for the bug and began deploying it at **17:25 UTC**.

## Permanent fix (as listed by Fastly)

| Action | Pattern it addresses |
|---|---|
| Deploy the bug fix across the network "as quickly and safely as possible" | Remove the latent bug |
| Complete post mortem of processes and practices during the incident | Learning |
| Find out why the bug wasn't detected in software QA and testing | Test gaps |
| Evaluate ways to improve remediation time | Faster mitigation |
| Longer term: continued investment in platform safety, including the isolation capabilities of WebAssembly and Compute@Edge | Tenant isolation |

Fastly also wrote: "Even though there were specific conditions that triggered this outage, we should have anticipated it."

## In my stack

| Same risk in my tools | How I'd prevent it |
|---|---|
| Multi-tenant platform (shared ingress controller, shared API gateway) where one team's config can crash it for everyone | Validate configs before applying (`nginx -t`, admission webhooks); separate ingress controllers for critical tenants ([K8s 69](../../CKA-Certification-Course-2025/notes/69-ingress-concepts.md)) |
| A bad Ingress annotation/snippet breaks the shared controller | Disable risky features (e.g. configuration snippets) for tenants; policy checks |
| Latent bugs found only by rare inputs | Fuzz testing; canary with diverse real configs; fast kill per tenant |
| Being a customer of a CDN | Multi-CDN or a fallback path for critical properties; know what happens when your CDN fails (topic 39) |

## Follow-up questions

1. **Q: What was the real root cause: the customer or the bug?**
   A: The bug. The customer's configuration was valid. The root cause was a latent software defect introduced on 12 May that testing didn't catch, on a platform where one tenant's config could affect most of the network.

2. **Q: How was it detected, and why wasn't the bug caught earlier?**
   A: Fastly's monitoring detected the disruption within a minute. The bug wasn't caught in May because it needed a specific configuration and circumstances that testing didn't cover; Fastly committed to finding out exactly why.

3. **Q: What would you check first?**
   A: What changed right before 09:47 — here, configuration pushes rather than a code deploy (the code had been running for weeks). That's why the "what changed?" list must include config.

4. **Q: How did they stop the impact?**
   A: By disabling the triggering configuration, without needing to roll back software.

5. **Q: What changed permanently?**
   A: The bug fix, a review of QA/testing and remediation time, and longer-term isolation work.

6. **Q: How would you confirm the fix?**
   A: Reproduce the trigger in a test environment with the fix and show no failure; fuzz similar configurations.

7. **Q: What if disabling the config hadn't worked?**
   A: Roll back the 12 May software to the previous version — slower and riskier after weeks of other changes, which is why fast per-tenant disable switches are valuable.

8. **Q: How would you prevent this class of incident?**
   A: Isolation between tenants, staged config distribution, fuzzing of config parsers, and fast kill switches per tenant/config.

9. **Q: What would you do differently?**
   A: Treat 40 minutes to find the trigger as the improvement target: tooling that shows which recent config changes correlate with errors.

10. **Q: What does this teach a company that **uses** a CDN?**
    A: Your availability includes your CDN's. For critical services, keep a second CDN or an origin bypass ready, and know how fast you can switch DNS.
