## ⚡ Core: the 10-minute version

**The idea.** An engineer was debugging slow S3 billing. Following an established playbook, they ran a command to remove **a small number of servers**. **One input was entered incorrectly**, and a **much larger set** of servers was removed, including servers supporting two critical subsystems. Those subsystems needed a **full restart**, and S3 in us-east-1 couldn't serve requests until they were back.

```
Playbook command + wrong input ──► too many servers removed
     ──► index + placement subsystems lose capacity ──► full restart needed
          ──► restart slow (not done in years, huge growth) ──► S3 us-east-1 down ~hours
               ──► EC2 launches, EBS (from snapshots), Lambda, S3 console affected
               ──► AWS status page can't be updated (it depended on S3)
```

**Picture it.** A hospital where a cleaner, following the checklist, means to unplug one machine but the label points to a whole power strip. Several life-support systems go off and take hours to restart safely.

**The one thing to know.** AWS's fix was **not** "be more careful". It was: **the tool now removes capacity slowly and refuses to go below a minimum.** Make tools safe, not people perfect.

**You've got it if you can:** explain the trigger, why recovery was slow, and the two tool changes AWS made.

## Summary

On 28 February 2017, an authorised S3 team member ran a command from an established playbook to remove a small number of servers used by the S3 billing process. One input was entered incorrectly, removing a larger set of servers that also supported S3's **index** and **placement** subsystems in us-east-1. Both needed a full restart, during which S3 could not serve requests; normal operation returned at 1:54 PM PST.

## Impact

| Item | Detail (from AWS's summary) |
|---|---|
| Region | US-EAST-1 (Northern Virginia) |
| S3 | Unable to service requests while the subsystems restarted |
| Other AWS services | S3 console, **new EC2 instance launches**, **EBS volumes** (when data was needed from an S3 snapshot) and **AWS Lambda** were impacted; other services had backlogs after S3 recovered |
| Status page | The AWS Service Health Dashboard (SHD) could not be updated until 11:37 AM PST because its admin console depended on S3 |
| Duration | From 9:37 AM to 1:54 PM PST is **about 4 hours 17 minutes** (calculated from AWS's timestamps; AWS does not state a total) |
| Customers affected / cost | **Not publicly disclosed** |

## Timeline (PST, from AWS's summary)

| Time | Event |
|---|---|
| — | S3 team debugging an issue making the S3 billing system progress more slowly than expected |
| **9:37 AM** | Playbook command run; one input wrong → larger set of servers removed (incl. index and placement subsystems) |
| 9:37 → | Index and placement subsystems require a full restart; S3 cannot service requests. Team uses **@AWSCloud Twitter** and SHD banner text for updates |
| **11:37 AM** | Until this time the SHD couldn't show per-service status |

| **1:54 PM** | Placement subsystem recovered (PUTs); **S3 operating normally** |
| After | Other services work through backlogs |

## How it happened

```
                   ┌───────────────────────────── S3 in us-east-1 ─────────────────────────────┐
 playbook command  │  billing subsystem servers  (target: a few)                               │
 + one wrong input │        │                                                                  │
 ─────────────────►│        └── larger set removed, including servers for:                     │
                   │              • INDEX subsystem  (metadata + location of every object;     │
                   │                needed for GET, LIST, PUT, DELETE)                         │
                   │              • PLACEMENT subsystem (allocates storage for new objects;    │
                   │                needs INDEX; used by PUT)                                  │
                   └───────────────────────────────────────────────────────────────────────────┘
 Capacity below what they need → both require FULL RESTART → S3 can't serve requests until done
```

Step by step:
1. The team was debugging slow billing processing.
2. They used an **established playbook** (a documented procedure). Nothing unusual about running it.
3. **One input was entered incorrectly.** The tool accepted it.
4. AWS: "the tool used allowed too much capacity to be removed too quickly."
5. Losing a significant portion of capacity forced **full restarts** of index and placement.
6. AWS: they had "not completely restarted the index subsystem or the placement subsystem in our larger regions for many years", and S3 had "experienced massive growth", so restarting and running the metadata integrity safety checks "took longer than expected".

## Why it spread

- **Blast radius:** the index subsystem serves **all** objects in the region, so one subsystem's restart meant all of S3 us-east-1.
- **Dependencies:** EC2 launches, EBS (snapshot-based volumes), Lambda and the S3 console depended on S3 (topic 39).
- **The status page depended on the thing that was down** (topic 44): the SHD admin console needed S3.
- **No safety limit in the tool:** nothing stopped a removal that took subsystems below minimum capacity.
- **Untested cold start:** a full restart at this scale hadn't been exercised in years.

## How they found it

AWS's summary does **not** describe how the issue was detected or what was checked first (**not publicly disclosed**). It does say the SHD couldn't be updated, so the team communicated through Twitter and banner text.

## What they did to fix it

1. **Restart the index subsystem** (with metadata integrity checks). At 12:26 PM, enough capacity for GET/LIST/DELETE; fully recovered at 1:18 PM.
2. **Then recover placement** (it depends on index), restoring PUTs by 1:54 PM.
3. **Let dependent services drain their backlogs.**
4. **Communicate** via Twitter and SHD banner text while the dashboard was unusable.

## Permanent fix (as listed by AWS)

| Change | Pattern it addresses |
|---|---|
| Tool modified to **remove capacity more slowly** | Human error → limit speed of damage |
| **Safeguards prevent removing capacity** if any subsystem would go **below its minimum required capacity** | Tool guardrails (topic 40) |
| **Auditing other operational tools** for similar safety checks | Fix the class, not the instance |
| Changes to **improve recovery time** of key S3 subsystems | Cold-start speed |
| Index subsystem **partitioning into smaller cells**, reprioritised to begin immediately | Blast radius reduction |
| SHD admin console changed to **run across multiple AWS regions** | Monitoring/status independence |

## Follow-up questions

1. **Q: What was the real root cause, not just the trigger?**
   A: The trigger was a mistyped input. The root cause was a tool that allowed too much capacity to be removed too quickly with no minimum-capacity check, combined with critical subsystems that hadn't been fully restarted in years at a much larger scale, so recovery was slow.

2. **Q: How was it detected, and why wasn't it caught earlier?**
   A: AWS doesn't say how it was detected. It couldn't be "caught earlier" in the usual sense because the damage was instant; prevention had to be in the tool.

3. **Q: What would you check first in a situation like this?**
   A: What the command actually did (which servers/subsystems lost capacity) and whether the removal was still in progress, then which subsystem must come back first (index before placement).

4. **Q: How did they stop the impact?**
   A: By restarting the index subsystem, then placement, with integrity checks, and communicating through channels that didn't depend on S3.

5. **Q: What did they change permanently?**
   A: Slower capacity removal, a minimum-capacity safeguard, an audit of other tools, faster recovery work, cell-based partitioning of the index subsystem, and a multi-region status dashboard.

6. **Q: How would you confirm the fix in your own systems?**
   A: Try the dangerous operation in staging with a deliberately wrong input and verify the tool refuses or limits it; time a full cold restart in a game day.

7. **Q: What if the restart itself had failed?**
   A: You'd need a fallback: restore metadata from backups or replicas, or route traffic to another region. That's why cold-start procedures must be tested.

8. **Q: How would you prevent this class of incident?**
   A: Guardrails in every tool that removes capacity (rate limits, minimums, previews, confirmations), cells to limit blast radius, and regular cold-start drills.

9. **Q: What would you do differently next time?**
   A: Host status and incident tooling outside the affected service/region from the start.

10. **Q: What if the same mistake happened during peak traffic in a single-region company?**
    A: Every customer would be down for the full restart. Multi-region read paths, or at least graceful degradation (serve cached content), would reduce the impact.
