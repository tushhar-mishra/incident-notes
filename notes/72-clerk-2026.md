## ⚡ Core: the 10-minute version

**The idea.** Clerk provides authentication for other companies' apps. PostgreSQL periodically runs **ANALYZE** to collect statistics about tables, which the **query planner** uses to pick an execution plan. For one column, the true fraction of NULL values was very high (**99.9996%**), but not 100%. On 19 February 2026, auto-ANALYZE's **sample was too small**, found **only NULLs**, and concluded the column was **100% NULL**. The planner chose a plan based on that, and the query ended up traversing far more rows than expected, consuming "nearly all database resources".

```
auto-ANALYZE (small sample) → "column is 100% NULL" (truth: 99.9996%)
   → planner picks a plan that's only good if that were true → query plan FLIP
   → one hot query eats nearly all DB resources → requests queue → >95% of traffic: 429
   → customer with aggressive retries spikes → team suspects the customer → blocks them → no change
   → session failover doesn't trigger (DB "technically still online, just degraded")
   → new failover path enabled (17:08) → partial recovery
   → 17:25 root cause found → 17:27 manual ANALYZE → plan returns → recovery (~90 min total)
```

**Picture it.** A sat-nav estimates traffic from a quick sample of cars. One morning its sample happens to see no cars on a small road and declares it "always empty", routing everyone down it. The road jams completely, and you spend time blaming one delivery company whose vans keep circling.

**The one thing to know.** **A database can break with no deploy at all.** Watch for **sudden per-query latency changes**, and know how to compare plans and refresh statistics quickly.

**You've got it if you can:** explain how a statistics sample can cause an outage and why the customer's retries were a symptom.

## Summary

On 19 February 2026, PostgreSQL's automatic ANALYZE collected a sample too small to see any non-NULL values in a column that was 99.9996% NULL, leading the planner to assume it was 100% NULL and flip to an inefficient query plan. The query consumed nearly all database resources, and over 95% of Clerk's traffic returned HTTP 429 for about 90 minutes. A customer's aggressive retries initially misled responders; manually re-running ANALYZE restored the previous plan.

## How it happened

```
Table with a column that is 99.9996% NULL
   auto-ANALYZE → random sample (too small) → sees only NULLs → stats: null_frac = 1.0 (100%)
   planner: "this condition can never match non-NULL rows" → chooses a plan accordingly
   reality: some non-NULLs exist → query traverses far more rows than estimated (over 17,000 per Clerk)
   → that query, run frequently, consumes nearly all DB resources
   → request handlers queue → load shedding/limits → 429s for >95% of requests
```

Clerk didn't name the table, query or the exact plan types (**not publicly disclosed**). It did explain the statistic: the planner estimates the fraction of NULLs; "the planner's sample size was too low and it only found NULL values, which led it to erroneously conclude that 100% of the values were NULL."

## Why it spread

- **One hot query** on a shared database affected every API depending on that database.
- **Misleading signal:** a customer's aggressive retries looked like the trigger; blocking them didn't help.
- **Failover keyed on "down", not "degraded":** the database was online but useless, so the session failover didn't trigger.
- **New failover not yet automated:** it existed but "hadn't been instrumented with triggers in production yet", and the team wasn't fully trained on enabling it.

## How they found it

The incident was reported and escalated internally at 16:15; the post doesn't name the monitoring signals or tools used (**not publicly disclosed**). After ruling out the customer (16:50) and finding the failover gap (16:55), they identified the plan flip at 17:25. Clerk says it lacked alerting for this class of issue: "we need to detect it immediately rather than relying on downstream symptoms."

## What they did to fix it

1. Enabled a **new failover** for session token generation (17:08) → partial recovery.
2. **Re-ran ANALYZE** on the affected table (17:27) → the query returned to its prior plan.
3. Later that evening: **refactored the query** so the planner takes a deterministic approach.
4. **Increased the statistics target** on the table so ANALYZE samples more rows.

## Permanent fix (as listed by Clerk)

| Change | Pattern it addresses |
|---|---|
| **Dedicated alerting for database query plan flips** | Detection |
| Session token failover that triggers on **any** failure at origin (not just Postgres outages), with automatic triggers (expected within weeks) and training | Degraded-but-up failures |
| **Audit all queries** for similar risk from unstable statistics | Find the class |
| Incident comms: dedicated communications lead, regular status updates even when unchanged, accurate severity labels, cross-posting to social channels | Communication (topic 06) |

## In my stack

| Same risk in my tools | How I'd prevent it |
|---|---|
| PostgreSQL tables with very skewed columns | `ALTER TABLE ... ALTER COLUMN ... SET STATISTICS 1000;` then `ANALYZE`; extended statistics where useful |
| No per-query latency monitoring | `pg_stat_statements` + alerts on mean time jumps per query (topic 31) |
| Health checks/failover that only test "is the DB up?" | Check query latency/success, not just connectivity (topic 29) |
| Blaming the loudest client first | Ask "is their traffic a cause or a reaction to our errors?" — retries spike **after** failures (topic 36) |
| Plan regressions after upgrades/large loads | Compare `EXPLAIN` output before/after; test with production-size data |

## Follow-up questions

1. **Q: What was the real root cause?**
   A: Auto-ANALYZE took a sample too small for a highly skewed column, producing wrong statistics; the planner flipped to an inefficient plan for a hot query. Contributing: no plan-flip alerting, failover that only triggered on full outages.

2. **Q: How was it detected, and why was diagnosis slow?**
   A: Escalated internally within minutes. Diagnosis was slowed by a misleading signal (a customer's retry spike) and by a failover that didn't trigger.

3. **Q: What was checked first?**
   A: The suspicious customer traffic; blocking it didn't help, which ruled it out.

4. **Q: How did they stop the impact?**
   A: Partial relief via a new failover path, then re-running ANALYZE to restore the good plan.

5. **Q: What changed permanently?**
   A: Plan-flip alerting, broader and automated failover, a query audit, more stable statistics, and better incident comms.

6. **Q: How would you confirm the fix?**
   A: The query's latency in `pg_stat_statements` back to baseline; `EXPLAIN` shows the expected plan; the larger statistics target persists across future ANALYZE runs.

7. **Q: What if re-running ANALYZE had produced the bad plan again?**
   A: Raise the statistics target first, or rewrite/hint the query, or add an index that makes the good plan clearly cheaper.

8. **Q: How would you prevent this class of incident?**
   A: Per-query latency alerts, stable statistics for skewed columns, deterministic query shapes, and failover on "degraded" not just "down".

9. **Q: Why is "no deploy happened" not reassuring for databases?**
   A: Databases change their own behaviour: statistics refresh, autovacuum, data growth, cache contents. "What changed?" must include these.

10. **Q: What if this happened at 10× traffic?**
    A: The bad query would saturate the database faster, and retries would pile on harder. Per-query timeouts and load shedding limit the damage while you fix the plan.
