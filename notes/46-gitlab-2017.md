## ⚡ Core: the 10-minute version

**The idea.** GitLab.com was fighting a load spike (suspected spam), which made the **secondary** database fall behind and break replication. While trying to re-sync it late at night, an engineer wiped the database directory, **thinking they were on the secondary**. They were on the **primary**. About **300 GB** was removed before they stopped it. Then they found that **none of their normal backups worked**.

```
Spam load → replication lag → replication broken → manual resync attempts
   → engineer wipes data directory on PRIMARY (meant SECONDARY) → ~300 GB gone
      → pg_dump backups: EMPTY (version mismatch, failure emails rejected)
      → Azure disk snapshots: NOT ENABLED for DB servers
      → secondary: already wiped for the resync
      → saved by: an LVM snapshot taken manually ~6 hours earlier
         → copy over slow disks ~18 hours → ~6 hours of data lost
```

**Picture it.** You're tired, fixing the spare tyre in the dark, and you deflate the tyre you're driving on. Then you open the boot: the spare is missing, the repair kit is empty, and the breakdown service number goes to voicemail.

**The one thing to know.** The deletion was one mistake. The **outage size** came from untested backups. **A backup you haven't restored is not a backup.**

**You've got it if you can:** list the backup methods and why each failed, and the action items that would have prevented each.

## Summary

On 31 January 2017, while trying to re-synchronise a broken PostgreSQL replica, a GitLab engineer accidentally wiped the database directory on the **primary** database server. The team then discovered that their backup procedures had not been working, and restored from an LVM snapshot taken about six hours earlier, losing about six hours of database data. GitLab.com was down for about 18 hours.

## Impact

| Item | Detail (from GitLab's postmortem) |
|---|---|
| Data removed | Around **300 GB** before the process was stopped |
| Data lost | Database changes from **17:20 UTC to about 23:30 UTC on 31 January** (the post also says "17:20 and 00:00" in one place): **at least 5,000 projects, 5,000 comments and roughly 700 user accounts** |
| Not lost | Git repositories and wikis (only database data); GitLab self-managed, Enterprise and GitHost customers not affected |
| Downtime | GitLab.com **down for about 18 hours** |
| Cost | **Not publicly disclosed** |

## Timeline (UTC, from GitLab's postmortem)

| Time | Event |
|---|---|
| Jan 31, ~17:20 | An engineer takes an **LVM snapshot** of production for staging work (this snapshot later saves them) |
| ~19:00 | Load increase, suspected **spam**; users can't post comments. Part of the load: a background job deleting an employee's account that had been wrongly flagged for abuse |
| ~23:00 | Secondary's replication **fails**: WAL segments it needed were already removed from the primary (no WAL archiving) |
| ~23:00–23:30 | Manual resync attempts: `pg_basebackup` hangs; `max_wal_senders` raised 3 → 32; PostgreSQL won't restart (too many semaphores) until `max_connections` lowered 8000 → 2000; `pg_basebackup` still appears stuck |
| ~23:30 | Engineer suspects leftover files in the secondary's data directory are the problem |
| Shortly after (exact time not stated) | Engineer wipes the data directory — **on the primary**. Stopped "a second or two" later; ~300 GB gone |
| After | Team searches for backups: pg_dump S3 bucket **empty**, Azure DB snapshots **not enabled**; decide to use the ~6-hour-old LVM snapshot |
| ~18 hours | Copying the data from staging over slow disks (~60 Mbps throttled) |
| Feb 1, 17:00 | Database restored (without webhooks) |
| Feb 1, ~18:00 | Final steps (webhooks restored, checks) done |

The exact time the outage was declared over is **not stated** beyond these.

## How it happened

```
          PRIMARY db1 ───(streaming replication)───► SECONDARY db2
                │                                          │
   heavy load (spam + job)                    lag → WAL already gone → replication BROKEN
                │                                          │
                │                 resync plan: empty db2's data dir, run pg_basebackup
                │                                          │
   engineer, in the wrong terminal ─── wipes data dir ─────┘  (thought: db2)
                ▼
          PRIMARY's data deleted (~300 GB)

Backups:  pg_dump (daily → S3)   ✗ ran pg_dump 9.2 against PostgreSQL 9.6 → error → no file
          failure alert emails    ✗ rejected (DMARC not set up for cron emails)
          Azure disk snapshots    ✗ not enabled for DB servers
          secondary (db2)         ✗ already emptied for the resync
          WAL archiving / PITR    ✗ not in use
          LVM snapshot (manual)   ✓ ~6 hours old → used
```

Step by step:
1. Load spike → replication lag → secondary couldn't catch up because the primary had already removed the needed WAL.
2. Re-syncing a replica was a **manual, undocumented** procedure. `pg_basebackup` waits silently for the primary — normal behaviour, but not documented in their runbooks — so the team thought it was broken.
3. Tired engineers, multiple terminals, similar-looking servers: the wipe ran on the primary.
4. The daily pg_dump had been **failing**: it ran on a server where the tooling defaulted to pg_dump 9.2 while the database was 9.6. Failure emails were rejected (DMARC). **Nobody owned** the backup procedure, so nobody tested it.

## Why it spread

- **No working backups** turned a recoverable mistake into 6 hours of data loss.
- **No WAL archiving / PITR** meant no way to replay changes after the snapshot.
- **The replica was not a backup:** it had been emptied as part of the resync (topic 32/34).
- **Slow restore path:** staging used cheap, slow storage, so copying took ~18 hours.

## How they found it

- The engineer noticed the mistake within a second or two and stopped the command.
- Then the team **looked for backups** and found the S3 bucket empty and the Azure snapshots disabled. GitLab: "the process of both finding and using backups failed completely."
- Earlier in the night, signals were: users unable to comment (load), replication lag/failure, `pg_basebackup` behaviour (investigated with `strace`, which showed it waiting in a poll call).

## What they did to fix it

1. Chose the **6-hour-old LVM snapshot** (the alternative was ~24-hour-old data).
2. Copied the data directory from staging to production — about **18 hours** because of slow disks.
3. Incremented database **sequences by 100,000** to avoid reusing IDs.
4. Restored **webhooks** carefully from a separate copy so deletion wasn't triggered.
5. Communicated in public: a public Google Doc of notes, a **YouTube live stream** of the recovery (peak ~5,000 viewers), and Twitter updates.

## Permanent fix (GitLab's action items, selected)

| Action item | Pattern it addresses |
|---|---|
| Shell prompt (PS1) that clearly shows host and environment | Wrong-host mistakes (topic 40) |
| Monitoring of backups with Prometheus; **automated testing of backup recovery** | Silent backup failure (topic 34) |
| PITR and continuous WAL archiving; investigate WAL-E / pgbarman | Recovery point |
| Hourly LVM snapshots; Azure disk snapshots for DB servers | More restore points |
| Replication documentation/runbooks; recover production replicas | Undocumented manual procedures |
| Sane `max_connections` | Config hygiene |
| Assign an **owner for data durability** | "Nobody owned it" |
| Spam-based user removal should not hard-delete | The original load trigger |

GitLab's stated principle: rather than preventing engineers from running commands, build an environment where you **can** make mistakes and recover quickly.

## Follow-up questions

1. **Q: What was the real root cause?**
   A: Not the engineer. The wipe was the trigger; the size of the outage came from backup procedures that silently failed (wrong pg_dump version, alerts rejected), no WAL archiving, disk snapshots not enabled, a manual undocumented replica resync, and no owner for data durability.

2. **Q: How was it detected? Why not earlier?**
   A: The wipe was noticed instantly. The broken backups were only discovered when needed; failure alerts were email-only and were being rejected.

3. **Q: What was checked first after the wipe?**
   A: Which backups existed and how fresh they were — to choose the best restore point (6-hour LVM snapshot vs 24-hour one).

4. **Q: How did they stop impact?**
   A: They couldn't avoid the downtime; they minimised data loss by picking the newest usable snapshot, and kept users informed publicly.

5. **Q: What did they change permanently?**
   A: Backup monitoring and automated restore testing, PITR/WAL archiving, more frequent snapshots, replication runbooks, environment-aware prompts and a data-durability owner.

6. **Q: How would you confirm backups are fixed?**
   A: Scheduled restore tests that restore into a scratch environment, verify data recency and counts, and record restore time vs RTO.

7. **Q: What if the LVM snapshot hadn't existed?**
   A: The next option was ~24-hour-old data. Without that, they'd have had to reconstruct from other sources. One lucky manual snapshot saved most of the day.

8. **Q: How would you prevent this class of incident?**
   A: Treat restore testing as a monitored production job; separate prompts and access for primary vs replica; automate replica rebuilds instead of manual commands at night.

9. **Q: What would you do differently in the moment?**
   A: Stop late-night manual work on the primary-replica pair after hours of firefighting; hand over to a fresh engineer; have a second person confirm the host before destructive commands.

10. **Q: What if this happened today on a managed database (e.g. RDS)?**
    A: Automated backups with PITR would likely cut data loss to minutes — but only if retention is configured and restores are tested, and deletion protection and separate-account backup copies exist.
