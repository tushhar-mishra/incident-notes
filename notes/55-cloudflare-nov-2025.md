## ⚡ Core: the 10-minute version

**The idea.** Cloudflare's Bot Management uses a **feature file** (the inputs for its bot-detection model), regenerated **every five minutes** from a **ClickHouse** query and pushed to every server. At 11:05 UTC, a database change made table metadata in an underlying database (`r0`) visible to the query, so the query started returning **duplicate rows**. The feature file **doubled**, exceeding the proxy's **limit of 200 features** (normal use ~60). The Rust proxy code **panicked**. Core traffic failed globally.

```
11:05 ClickHouse permission change (rolled out gradually across the cluster)
   → query without a database-name filter now returns duplicates from "default" AND "r0"
   → feature file doubles → > 200 features → FL2 proxy: unwrap() on Err → panic → HTTP 5xx
   → file regenerated every 5 min: good file if the query hit an un-updated node, bad file if updated
   → network flips between broken and working → looks like an attack
14:24 stop generating/propagating new files → 14:30 known-good file pushed, proxies restarted
17:06 all services resolved
```

**Picture it.** A shop prints tomorrow's price list every five minutes from a spreadsheet. Someone changes spreadsheet permissions, and the export suddenly lists every product twice. The till only has room for 200 lines, so it crashes. Sometimes the export runs on an old copy and the tills work again — so staff think someone is attacking the tills.

**The one thing to know.** **Config generated by your own systems can be as dangerous as user input.** Validate it (size, duplicates, limits) before distribution, and make readers **keep the last good file** instead of crashing.

**You've got it if you can:** trace the chain from a permission change to a proxy panic, and explain why the outage flickered.

## Summary

On 18 November 2025, a change to ClickHouse database permissions caused the query that builds Cloudflare's Bot Management feature file to return duplicate rows. The file doubled in size and exceeded a 200-feature limit in Cloudflare's core proxy, causing the newer FL2 proxy to panic and return HTTP 5xx errors (and the older FL proxy to assign every request a bot score of zero). Because the file was regenerated every five minutes from a cluster being updated gradually, the failure fluctuated at first; core traffic was largely restored at 14:30 UTC and all services by 17:06 UTC. Cloudflare called it its worst outage since 2019.

## Impact

| Item | Detail (from Cloudflare's postmortem) |
|---|---|
| Core CDN and security | HTTP **5xx** for traffic depending on the bots module (FL2 proxy) |
| Older FL proxy | No errors, but **bot score 0** for all traffic → bot-blocking rules produced false positives |
| Workers KV | Significantly elevated 5xx (its front end depends on the core proxy) |
| Turnstile | Failed to load (11:30–13:10 and 14:40–15:30) |
| Dashboard | Mostly up, but most users couldn't log in (Turnstile on the login page) |
| Access | Widespread authentication failures until 13:05; existing sessions unaffected |
| Email Security | Processing and delivery unaffected; some reduced spam-detection accuracy |
| Severity | "Cloudflare's worst outage since 2019"; "the majority of core traffic" stopped flowing |
| Cause type | Not a cyber attack or malicious activity |
| Request counts / cost | **Not publicly disclosed** |

## How it happened

```
ClickHouse:  database "default" (distributed tables)  ──reads──►  database "r0" (underlying tables)
11:05 change: make access to r0 metadata explicit (finer-grained permissions)
   │
   └─► metadata query used for the feature file: "list columns for table X"  (no filter on database name)
          before: rows from "default" only
          after : rows from "default" AND "r0"  → duplicate features
   │
   ▼
Feature file (~60 features normally) → doubled, > 200 features
   │   generated every 5 min, on a cluster being updated node by node:
   │   query on updated node → BAD file;  on old node → GOOD file   → flapping
   ▼
Core proxy bots module: preallocated memory for max 200 features
   FL2 (Rust):  limit exceeded → Result::Err → .unwrap() → panic → 5xx
   FL (old):    no crash, but bot scores = 0 for everyone
```

## Why it spread

- **Global, automatic distribution** of the feature file every five minutes.
- **No validation** of the generated file's size/duplicates before distribution; the reader treated an oversized file as a fatal error.
- **Core dependency:** many products (Workers KV, Access, Turnstile, Dashboard login) sit behind the core proxy.
- **Flapping** misled responders toward an attack theory; the coincidental status page failure strengthened it.
- **Debugging load:** debugging and observability systems consumed large amounts of CPU, increasing latency.

## How they found it

- Automated test at 11:31; incident call at 11:35.
- Initial focus: degraded **Workers KV**; suspicion of a large **DDoS** (fluctuations, status page down).
- By 13:37, the team identified the Bot Management configuration file as the trigger; at 14:24 a test with an old file confirmed recovery.

## What they did to fix it

1. **Bypassed** the core proxy for Workers KV and Access (fallback to a prior proxy version) to reduce impact (13:05).
2. **Stopped** generation and propagation of new feature files (14:24).
3. **Manually inserted a known-good file** into the distribution queue and **forced a restart** of the core proxy (14:30).
4. Restarted remaining services in bad states; scaled control-plane concurrency for the dashboard backlog.

## Permanent fix (as listed by Cloudflare)

| Remediation | Pattern it addresses |
|---|---|
| **Harden ingestion of Cloudflare-generated configuration files** "in the same way we would for user-generated input" | Internal config is untrusted input |
| **More global kill switches** for features | Fast disable |
| Prevent **core dumps or other error reports** from overwhelming system resources | Debugging load during incidents |
| **Review failure modes** for error conditions across all core proxy modules | Crash vs degrade |

Cloudflare later ran a resilience programme called "Code Orange: Fail Small" (announced complete in May 2026).

## In my stack

| Same risk in my tools | How I'd prevent it |
|---|---|
| A CronJob that generates a config from a DB query and pushes it to all pods | Validate output (row counts, size vs previous, duplicates) before publishing; publish to a canary first |
| SQL queries against `information_schema` without a schema/database filter | Always filter explicitly; test after permission changes |
| Rust `unwrap()` / Go `panic` / unchecked exceptions on config load | Return errors, keep last good config, alert |
| Fixed-size limits in code | Alert when usage approaches the limit (e.g. > 50%) |
| Hypothesis lock-in ("it's an attack") | IC asks "what else changed?" at fixed intervals (topic 07) |

## Follow-up questions

1. **Q: What was the real root cause?**
   A: A metadata query without a database filter, which returned duplicates after a permissions change; no validation of the generated file; and a reader that panicked on exceeding a fixed limit. The permission change was the trigger.

2. **Q: How was it detected, and why did diagnosis take time?**
   A: An automated test fired at 11:31. Diagnosis took about two hours because the failure flapped every few minutes (good and bad files alternating) and the status page went down coincidentally, pointing the team toward a DDoS theory.

3. **Q: What was checked first?**
   A: Workers KV errors and the possibility of an attack; then the Bot Management module was identified as the source of 5xx.

4. **Q: How did they stop the impact?**
   A: Stopped generating new files, pushed a known-good file manually, restarted the proxy; earlier, bypassed the proxy for KV and Access.

5. **Q: What changed permanently?**
   A: Treat internally generated config like user input, more global kill switches, prevent error reports from overwhelming systems, review error handling across proxy modules.

6. **Q: How would you confirm the fix?**
   A: Feed an oversized/duplicate-filled file in testing and verify it's rejected before distribution, and that the proxy keeps the last good file if one gets through.

7. **Q: What if the known-good file had been unavailable?**
   A: Disable the Bot Management module globally (a kill switch) and serve traffic without bot scores — degraded but up. That's why "more kill switches" was a remediation.

8. **Q: How would you prevent this class of incident?**
   A: Validate generated config, stage its rollout, fail soft in readers, and alert on usage approaching hard limits.

9. **Q: What would you do differently during response?**
   A: Periodically re-check "what changed?" across all systems, not just recent deploys; fluctuating failures often mean something is regenerated on a timer.

10. **Q: Why did the old FL proxy not crash, and why is that still bad?**
    A: It handled the error without crashing but produced bot score 0 for everyone. That's a silent correctness failure: customers with bot-blocking rules blocked legitimate users. Degraded modes must be safe, not just "not crashing".
