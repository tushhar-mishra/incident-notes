## ⚡ Core: the 10-minute version

**The idea.** Cloudflare's systems decide **which data centers announce which IP prefixes** (the "service topology"). On 6 June 2025, a config for a new, not-yet-live service accidentally included the **1.1.1.1 resolver's prefixes**. Because the new service wasn't live, nothing changed and no alerts fired. On 14 July, another change to that service attached a **test location**, which triggered a **global refresh**: 1.1.1.1's topology became "one offline location", so its prefixes were **withdrawn everywhere**. For **62 minutes**, most 1.1.1.1 users couldn't resolve names.

```
Jun 6  config for future DLS service accidentally includes 1.1.1.1 prefixes   → dormant, no alerts
Jul 14 21:48 change: attach a (non-live) test location to that service        → global config refresh
       21:52 1.1.1.1 topology = single offline location → prefixes withdrawn → queries drop globally
       22:01 alerts, incident declared
       22:20 revert → prefixes re-advertised, ~77% traffic back
       22:54 remaining ~23% of servers manually reconfigured → normal
```

**Picture it.** In June, someone fills in a form for a branch office that hasn't opened yet and accidentally lists the head office's phone numbers on it. Nothing happens. In July, they add a temporary desk to the unopened branch; the phone company re-reads the whole form and moves the head office's numbers to the closed branch. All calls to head office go nowhere.

**The one thing to know.** **A change can be "safe" today and dangerous later.** Dormant config must be validated when it's written, and every change that triggers a **global** refresh needs **staged** deployment.

## Summary

On 14 July 2025, Cloudflare's 1.1.1.1 public DNS resolver was unavailable to most users for 62 minutes. A June configuration error for a not-yet-live Data Localization Suite (DLS) service had accidentally linked the 1.1.1.1 prefixes to that service; a July change to the same service triggered a global configuration refresh that reduced 1.1.1.1's topology to a single offline location, withdrawing its prefixes worldwide. Cloudflare reverted the change and manually restored IP bindings on part of its fleet.

## Impact

| Item | Detail (from Cloudflare's post) |
|---|---|
| Duration | **62 minutes**: unavailable from 21:52 to 22:54 UTC |
| Users | "The majority of 1.1.1.1 users globally were affected" (no percentage given) |
| Protocols | Immediate, significant drop over **UDP, TCP and DNS over TLS (DoT)** |
| DNS over HTTPS | **Mostly unaffected**: `cloudflare-dns.com` uses different IP addresses |
| Gateway DNS | Intermittent degradation |
| Prefixes withdrawn | Including 1.1.1.0/24, 1.0.0.0/24, 2606:4700:4700::/48 and others |
| Cause type | Internal configuration error; not an attack or BGP hijack |

## How it happened

```
Service topology (which locations announce which prefixes)
  legacy system: hard-coded lists of data centers attached to prefixes; changes NOT progressively deployed
  strategic system: describes topologies without hard-coding; supports staged deployment
  (both in use, kept in sync)

Jun 6: new DLS service config ── includes ──► 1.1.1.1 prefixes (by mistake)   [DLS not live → no effect]
Jul 14: add test location to DLS service ──► global refresh of related routes
        ──► 1.1.1.1 topology := { single, offline location }
        ──► 1.1.1.1 prefixes withdrawn from all locations at once
```

Cloudflare: the legacy approach of hard-coding location lists "has proved error-prone" and its updates "do not follow a progressive deployment methodology". The change was peer-reviewed, but "didn't go through a series of canary deployments".

## Why it spread

- **Global refresh, no canary:** the legacy system pushed the topology change everywhere at once.
- **Anycast:** 1.1.1.1 is served from all locations using the same addresses; withdrawing the prefixes everywhere makes the service vanish globally.
- **Recovery friction:** after the revert, about **23% of edge servers** had lost IP bindings and needed reconfiguration through change management, which isn't instantaneous by design (for safety).

## How they found it

**Internal service health alerts** at 22:01 (query, proxy and data center failures); the team saw traffic to the resolver prefixes had dropped drastically and that resolver routes were missing from servers. The June error raised no alerts because it changed no traffic.

## What they did to fix it

1. **Reverted** to the previous configuration (22:20) → prefixes re-advertised, ~77% of traffic back.
2. **Accelerated** the change-management rollout to restore IP bindings on the remaining ~23% of servers (normal by 22:54).
3. Followed up with Tata Communications on the unrelated hijack.

## Permanent fix (as listed by Cloudflare)

| Remediation | Pattern it addresses |
|---|---|
| **Staged addressing deployments**: deprecate legacy components lacking staged deployment; use progressive, health-mediated processes | Global changes without canaries |
| **Deprecate legacy systems**: accelerate migration away from risky methods, with higher standards for documentation and test coverage | Dual systems kept in sync |

## In my stack

| Same risk in my tools | How I'd prevent it |
|---|---|
| Terraform/Helm values that reference resources "for later" | Validate references when written; policy tests that critical resources (DNS records, prefixes, LBs) are only attached where intended |
| One shared config object read by many services (e.g. a global ingress/LB config) | Split by service; staged rollout; diff of **effective** state before apply |
| Old and new systems both managing the same thing | Single source of truth; drift detection; finish migrations |
| Depending on a single public DNS resolver | Configure multiple resolvers from different providers; consider DoH/DoT on different IPs (topic 26) |

## Follow-up questions

1. **Q: What was the real root cause?**
   A: A legacy topology system that applied changes globally without staging, combined with a June config error that wrongly linked 1.1.1.1 prefixes to a non-production service. The July test-location change was the trigger.

2. **Q: Why didn't anyone notice in June?**
   A: The DLS service wasn't live, so the mistaken reference changed no traffic and fired no alerts. Validation at write time (not traffic-based alerts) would have been needed.

3. **Q: What would you check first?**
   A: Whether the prefixes were being announced at all (BGP visibility), then recent topology/config changes.

4. **Q: How did they stop the impact?**
   A: Revert to the previous config, then accelerated reconfiguration of servers that had lost IP bindings.

5. **Q: What changed permanently?**
   A: Moving addressing changes to staged, health-mediated deployment and deprecating the legacy system.

6. **Q: How would you confirm recovery?**
   A: Prefixes visible globally, query volume back to normal across UDP/TCP/DoT, and resolver routes present on all servers.

7. **Q: What if the revert had failed?**
   A: Manually re-attach the prefixes to the correct topology through the strategic system or by direct configuration on the edge, location by location.

8. **Q: How would you prevent this class of incident?**
   A: Validate configs for references to critical resources at write time, stage every topology change, and avoid dual systems for the same responsibility.

9. **Q: What was the BGP hijack, and why wasn't it the cause?**
   A: When Cloudflare withdrew 1.1.1.0/24, Tata Communications India's announcement of it became visible. Cloudflare says clearly it was not the cause; it appeared after the withdrawal.

10. **Q: What does this teach a company that relies on 1.1.1.1?**
    A: Configure at least two resolvers from different providers; DoH users of a different hostname/IP were mostly fine, showing the value of diverse paths.
