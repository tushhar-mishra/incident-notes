## ⚡ Core: the 10-minute version

**The idea.** Heroku runs customer apps ("dynos") on hosts. An **automated operating system update** ran on production hosts even though it should have been disabled. It **restarted the networking service**. The routes dynos needed were added by a **legacy script that only ran on initial boot**, so after the restart the routes were **gone** and dynos couldn't make outbound connections. Heroku's own tools and status page ran on the same affected infrastructure, slowing both the fix and the communication.

```
06:00 UTC  automated OS upgrade restarts host networking → routes (set only at boot) not reapplied
           → dynos (esp. Private Spaces) can't make outbound HTTP requests
08:26      core issue confirmed
11:54      missing network routes found (healthy vs unhealthy host comparison)
13:11      unexpected network service restart discovered
13:42      trigger pinpointed: automated upgrade of a system package
19:18      vendor update token invalidated → no further hosts affected
22:01      fleet-wide dyno recycle
05:50 (Jun 11) incident resolved
```

**Picture it.** An office whose phone lines are connected by a technician only on the day the building opens. One night, the building's automatic maintenance switches the phone system off and on. The lines aren't reconnected, and the office can't call out. The office's own emergency phone is on the same switchboard.

**The one thing to know.** **Any setting applied only at boot is a time bomb** for the day a service restarts without a reboot. Make configuration **declarative and re-applied** by the service that owns it — and keep incident tooling **off** the infrastructure it monitors.

## Summary

On 10 June 2025, starting at 06:00 UTC, an automated operating system update ran on Heroku's production infrastructure when it should have been disabled, restarting the hosts' networking services. Routing rules applied by a legacy script only at initial boot were not reapplied, cutting outbound connectivity for dynos on affected hosts. Heroku's internal tools and status page ran on the same infrastructure, slowing diagnosis and communication; many customers experienced up to 24 hours of downtime, and the incident was resolved at 05:50 UTC on 11 June.

## How it happened

Heroku named three issues:

| Issue | Heroku's description |
|---|---|
| **A Control Issue** | "An automated operating system update ran on our production infrastructure when it should have been disabled." It "restarted the host's networking services." |
| **A Resilience Issue** | The networking service "relied on a legacy script that only applied correct routing rules on initial boot." On restart, "the routes were not reapplied, severing outbound network connectivity for all dynos on the host." |
| **A Design Issue** | "Our internal tools and the Heroku Status Page were running on this same affected infrastructure." |

```
Host boot ──► legacy script adds routing rules ──► dynos have outbound connectivity ✓
...
06:00 automated OS upgrade ──► restarts networking service ──► routes cleared
     legacy script does NOT run again (boot only) ──► dynos: no outbound connectivity ✗
     same hosts run Heroku's internal tools + status page ──► slower diagnosis and comms
```

Heroku also stated: "A lack of sufficient immutability controls allowed an automated process to make unplanned changes to our production environment." Its later corrective-action post describes it as "an unintended system update applied to our production infrastructure by our vendor". The exact package name and vendor are **not publicly disclosed** in these posts.

## Why it spread

- The update ran across many hosts in the fleet.
- **No re-application** of routing state after a service restart.
- **Shared fate:** tools for diagnosing and the status page for communicating were on the affected infrastructure.
- **Diagnosis took time** ("tooling and process gaps"): from symptoms to missing routes to the restart to the package upgrade.

## How they found it

1. Monitoring detected networking errors at 06:00.
2. Confirmed outbound HTTP failures from Private Spaces dynos (08:26).
3. **Compared healthy vs unhealthy hosts** → missing routes (11:54).
4. Discovered an unexpected network service restart (13:11) → traced to an automated package upgrade (13:42).

## What they did to fix it

1. Rotating restarts of internal instances for relief (12:56).
2. Workaround to post status updates via X (13:58).
3. Worked with the upstream vendor to **invalidate the update token**, stopping further hosts being hit (19:18).
4. Restored the Dashboard (20:59), then a **fleet-wide dyno recycle** (22:01) to restore routes everywhere.
5. Worked through backlogs (emails, Heroku Connect, release phase).

## Permanent fix (status as of Heroku's September 2025 update)

| Action | Status |
|---|---|
| Disabled the automated upgrade service during the incident | Done (10 June) |
| **Permanent halt on all unattended vendor OS upgrades**; no system changes outside controlled deployment | Done |
| Audited images for other sources of mutation | Done |
| **Automated startup scripts for networking services** (routes survive restarts) | Done |
| Risk-based strategy for attended upgrades | Developed |
| Status site: CDN caching added; migrating to the Salesforce Trust site; backup incident communications channel | Done / in progress |
| Update cadence: at least every 30 minutes for Sev-0, every 60 minutes for Sev-1/2 | Adopted |
| Regression tests for dyno-to-dyno communication; canaries for long-running apps; monitoring of monitoring | Added |
| Streamlined engineer access and break-glass tooling | Done (procedures being revised) |
| OS drift monitoring; canaries for dyno network connectivity | Investigating / planned |

## In my stack

| Same risk in my tools | How I'd prevent it |
|---|---|
| Routes, iptables rules, sysctls or mounts set by a one-time boot script | Make them persistent and owned (NetworkManager/nmcli profiles, systemd units with `PartOf=`/`After=`, `/etc/sysctl.d`, fstab) ([Linux 060](../../linux-mastery-rhel/notes/060-networkmanager-and-nmcli.md), [Linux 098 · systemd unit files](../../linux-mastery-rhel/notes/098-systemd-unit-files.md)) |
| Unattended upgrades on production | Disable; patch via new images (topic 25) |
| Ansible "run once at provisioning" tasks | Make playbooks idempotent and re-run regularly to restore state ([Ansible 27 · Idempotency](../../Ansible/notes/27-idempotency-in-depth.md), [Ansible 55 · ansible-pull and drift](../../Ansible/notes/55-ansible-pull-and-drift.md)) |
| Status page / chat / runbooks on the same platform | Independent hosting (topics 06, 44) |
| Finding "what's different" between hosts | Keep a fast way to diff two hosts (packages, routes, services) |

## Follow-up questions

1. **Q: What was the real root cause?**
   A: Three things: an automated OS update that should have been disabled (control), routing rules applied only at boot and never re-applied (resilience), and tooling/status on the same infrastructure (design). The update was the trigger.

2. **Q: How was it detected, and why did diagnosis take so long?**
   A: Monitoring caught networking errors at 06:00. The cause took ~7.5 hours: first confirming outbound failures, then comparing hosts to find missing routes, then discovering the network service restart, then the package upgrade — with internal tools themselves impaired.

3. **Q: What would you check first?**
   A: Compare a broken host with a healthy one: `ip route`, `ip rule`, recent package changes (`/var/log/apt/history.log`), and `journalctl` for service restarts.

4. **Q: How did they stop the impact?**
   A: Invalidated the update token so no more hosts were affected, then recycled dynos fleet-wide.

5. **Q: What changed permanently?**
   A: Permanent halt of unattended OS upgrades, startup scripts so networking state is restored on restart, image audits, an independent status channel, and better canaries and monitoring.

6. **Q: How would you confirm the fix?**
   A: Restart the networking service on a canary host and verify dynos keep outbound connectivity; confirm no host has automatic upgrades enabled.

7. **Q: What if the dyno recycle hadn't restored connectivity?**
   A: Replace hosts from a known-good image, or apply the routes manually via configuration management while the permanent fix is built.

8. **Q: How would you prevent this class of incident?**
   A: Immutable infrastructure (no in-place changes), declarative networking that re-applies itself, and staged OS updates.

9. **Q: What would you do differently in communication?**
   A: Keep the status page and incident channels off the production platform and test that they work during a platform outage; Heroku's own fix includes a cadence of updates every 30–60 minutes.

10. **Q: How is this similar to Datadog 2023 (topic 63)?**
    A: Both: automatic OS updates outside the change process restarted network services, which removed routing state that other components had set. The common lesson: control every automatic change and make network state survive service restarts.
