## ⚡ Core: the 10-minute version

**The idea.** Code deploys usually go through canaries and staged rollouts. **Configuration** (feature files, rules, policies, flags, routing tables) is often pushed **globally within seconds**, because it needs to be fast (e.g. a new security rule). That's exactly why a bad config can take down **everything at once**.

```
Engineer/automation writes config ──► validation? ──► distribution system ──► ALL servers, worldwide, in seconds
                                                                              │
                     software that reads it hits an unexpected case ─────────► crash / 100% CPU everywhere
```

Real examples (Part 3): Cloudflare 2019 (a regex rule), CrowdStrike 2024 (a content file), Google Cloud 2025 (a policy with blank fields), Cloudflare November 2025 (a feature file that doubled in size), Azure Front Door October 2025 (valid customer configuration changes produced incompatible metadata that crashed edge servers after passing health checks).

**Picture it.** A city-wide traffic light system. Changing one intersection's timing is a local risk. A typo in the city-wide timing file, pushed to every light at once, gridlocks the whole city.

**The one thing to know.** **Treat config like code:** validate it, roll it out in **stages** (canary → region → global), make it **easy to roll back**, and make readers **fail safe** on bad input.

**Try it now:** list every system at your company that can change behaviour on **all** servers within a minute (flags, config service, WAF rules, DNS, CDN rules). Those are your biggest blast radiuses.

**You've got it if you can:** explain why config pushes are riskier than code deploys and describe a safe config pipeline.

## Symptoms

| Where | What you see |
|---|---|
| Graphs | **Simultaneous** failure across many servers/regions (not a gradual rollout pattern); step change |
| Processes | Crash loops everywhere (parser panics), or CPU at 100% everywhere |
| Logs | Errors about parsing, unexpected values, null/blank fields, size limits, `panic`, `unwrap()` on `Err` |
| Deploy history | **No code deploy** at the start time → people waste time looking at deploys |
| Audit log | A flag flip, a rule change, a policy update, a data file generation |
| Sometimes | Flapping (bad and good config alternate as a generator runs periodically) |

The **city-wide traffic lights** (Core). A **kill switch** is a big red button that turns the new timing plan off and returns every light to the old plan at once.

## How it happens

### The failure chain

1. **Input changes.** A person edits a rule, a policy, a flag; or an **automated** job generates a data file (and its input changed, e.g. a database query returns more rows).
2. **It looks valid.** It passes basic syntax checks; it may even be valid by design.
3. **A reader can't handle it.** The software reading it has a latent bug: a size limit, a null pointer, an expensive regex, an unhandled enum value.
4. **It's distributed everywhere fast**, by design, with no canary.
5. **Every reader fails the same way at the same time.** Redundancy doesn't help: all replicas have the same bug and the same input.
6. **Recovery is slow** if the bad config is sticky (cached, re-read on restart, or the system that would distribute the fix is itself broken).

### Why config is treated differently

| Code deploys | Config / data pushes |
|---|---|
| Minutes–hours, staged | Seconds, global |
| Canary, health checks | Often none ("it's just config") |
| Reviewed in PRs | Changed in a UI or generated by automation |
| Rollback = redeploy old image | Rollback = need the old version stored and a fast push path |
| Owned by the service team | Owned by another team/tool |

## How to find it

**First:** if the failure is **everywhere at once** and there's **no code deploy**, suspect config/data.

```bash
# What changed in config systems in the last hour?
git -C config-repo log --since="1 hour ago" --stat
kubectl get cm -A --sort-by=.metadata.creationTimestamp | tail     # creation only; use audit logs for updates
# Feature-flag tool: audit log ("who flipped what, when")
# Cloud: CloudTrail for parameter/flag changes (SSM Parameter Store, AppConfig)
aws cloudtrail lookup-events --lookup-attributes AttributeKey=EventName,AttributeValue=PutParameter --max-results 20
```

**Second:** read the crash message on any one instance; it usually names the input.

```
FATAL config load failed: rules.yaml: 1,412 entries exceeds max_entries=1000 (illustrative)
```
- Points to an input with more items than a fixed limit.

**Third:** compare the current config with the last good one: size, number of entries, new fields, blank values.

```bash
ls -l /etc/app/features/            # size jumped?
diff <(jq -S . last-good.json) <(jq -S . current.json) | head
```

## How to fix it

### Immediate

1. **Stop the propagation** (pause the generator/distributor; turn off the job).
2. **Push the last known good config** (or flip the flag back / kill switch).
3. **Restart** readers if they cache the bad config.
4. If the distribution system is itself broken, use the manual/backup path (that's why you need one).

### Permanent

- **Validate** before distribution: schema, size limits, counts, sanity (e.g. "reject if > 2× previous size"), and **test-load** it in a real reader.
- **Stage** config rollouts like code: canary hosts → one region → global, with automatic health checks between stages.
- **Readers fail safe:** on bad config, **keep the last good one** and alert, instead of crashing ("fail small"; Cloudflare's post-2025 programme used this name). Decide per system whether to **fail open** (allow traffic) or **fail closed** (block); e.g. Google's June 2025 report committed to Service Control failing open on bad policy data.
- **Feature flags** for risky code paths, so new behaviour can be disabled without a deploy.
- **Versioned config** with one-command rollback; audit logs.
- Treat **generated data** (from queries, ML models, threat feeds) as config with the same checks.

---

## How to verify the fix

- All instances running the last good config version (check a version/hash metric exposed by readers).
- Crash/CPU back to normal everywhere; error rate back in SLO.
- The generator/distributor is paused or fixed so the bad config can't come back on the next cycle.

---

## Prevention

- Each reader exports `config_version` and `config_load_errors_total` metrics; alert on load errors.
- Config pipeline with validation + staged rollout + auto-halt on errors.
- Regular **chaos tests** with malformed config ("what does the reader do with an empty file? a huge file?").
- Inventory of all global-push systems, each with a documented kill switch.

## Follow-up questions

1. **Q: What was the real root cause, not just "bad config"?**
   A: Example: an automatically generated feature file doubled in size because an upstream database query started returning duplicates after a permissions change; the reader had a fixed limit and crashed on exceeding it; the file was pushed globally every few minutes. Root causes: no size validation, a reader that crashes instead of keeping the last good file, and global distribution without stages.

2. **Q: How did you detect it? Why not earlier?**
   A: A global error spike. Not earlier because config pushes had no canary or health gate.

3. **Q: What did you check first?**
   A: Whether it was everywhere at once and whether a code deploy happened. No deploy + simultaneous = config/data push. Then the config audit log.

4. **Q: How did you stop impact quickly?**
   A: Stopped the generator, pushed the last good file, and restarted readers.

5. **Q: Permanent fix?**
   A: Size and sanity validation before publish; readers keep the last good config on load errors; staged rollout; kill switch.

6. **Q: How did you confirm?**
   A: Config version metric showed the good version everywhere; errors normal; generator fixed and re-enabled with validation, and it rejected a test bad file.

7. **Q: What if the system that pushes config was itself down?**
   A: You need a pre-planned out-of-band path: a manual push tool, a pinned config baked into the image as fallback, or a way to make readers ignore new config. Without it, recovery waits for the push system.

8. **Q: Fail open or fail closed?**
   A: Depends on the risk. A rate limiter or quota check can usually fail open (allow traffic) because blocking everyone is worse. An authentication or security filter may need to fail closed. Decide per system before the incident.

9. **Q: What would you do differently?**
   A: Treat every fast global config path as a production deploy pipeline with stages and validation.

10. **Q: What if the bad config was only bad for 1% of servers (a specific hardware type)?**
    A: A staged rollout would catch it only if the canary includes that hardware. Canary groups should be representative (every region, hardware type, OS version).
