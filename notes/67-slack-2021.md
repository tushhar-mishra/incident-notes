## ⚡ Core: the 10-minute version

**The idea.** On 4 January 2021, people returned to work with **cold caches**, so Slack clients pulled more data than usual. One of Slack's **AWS Transit Gateways** (TGWs — managed network hubs connecting VPCs, meant to scale automatically) became **overloaded** and **dropped packets**. Web servers waited on slow backends; the top-of-hour peak at 7:00 AM saturated them. Autoscaling first **scaled down** (waiting threads use little CPU), then **scaled up massively**. The service that sets up new servers hit the **Linux open files limit** and an **AWS quota**. Slack's dashboards also failed — they depended on the same TGW.

```
cold caches → traffic up → TGW doesn't scale fast enough → packet loss
  → web tier waits on backends → 7:00 AM mini-peak saturates web tier → Slack unavailable
  → autoscaling: low CPU → scale DOWN; then high thread use → scale UP (1,200 servers, 7:01–7:15)
  → provision-service hits open-files limit + AWS quota → broken instances
  → dashboards/alerting down (different VPC from their DB → also through TGW)
  → AWS manually increases TGW capacity → 10:40 AM network normal
```

**Picture it.** After a long holiday, everyone comes back to the office at 9 AM and tries to download all their missed emails at once. The building's network switch is slower to adapt than promised. The office manager, seeing staff "idle" (they're actually waiting for downloads), sends some home, then panics and tries to hire 1,200 temps at once — overwhelming HR's onboarding desk.

**The one thing to know.** **Autoscaling on the wrong signal makes things worse**, and the **machinery for recovery** (provisioning, dashboards) must be tested at **emergency scale** and kept **independent** of the failing path.

**You've got it if you can:** explain why autoscaling scaled down during an overload, and why Slack couldn't add servers fast.

## Summary

On 4 January 2021, one of Slack's AWS Transit Gateways became overloaded by the traffic pattern of the first working day after the holidays and began dropping packets. Higher latency to backends saturated Slack's web tier, making Slack unavailable; autoscaling then tried to add 1,200 servers, but Slack's provisioning service hit the Linux open-files limit and an AWS quota, while dashboards and alerting (which also depended on the TGW) went down. Slack recovered to a degraded state by about 9:15 AM PST, and the network returned to normal by 10:40 AM after AWS manually increased TGW capacity.

| Item | Detail (from Slack's postmortem) |
|---|---|

| Recovery | By about 9:15 AM PST "degraded, not down"; network normal 10:40 AM PST |
| Start time | **Not stated** (errors crept up during the Americas morning; Slack was paged by an external monitoring service) |

## How it happened

```
Slack VPCs ──── AWS Transit Gateway (TGW) ──── other Slack VPCs (backends, databases)
                       │
     first-Monday traffic (cold caches) → TGW didn't scale fast enough → packet loss
                       ▼
Web tier (Apache workers) waiting on slow backends
  autoscaling signal 1: CPU low (threads just waiting)   → scale DOWN   ✗
  autoscaling signal 2: worker-thread utilisation high   → scale UP big ✓ but...
                       ▼
provision-service (configures new instances, calls AWS APIs over the same degraded network)
  → Linux open files limit exceeded (most significant) + an AWS quota exceeded
  → many broken instances → autoscaling group hits its maximum size
Dashboards + alerting: in a different VPC from their database → depend on TGW → down
```

AWS later found the trigger; Slack: "By the time Slack had recovered, engineers at AWS had found the trigger."

## Why it spread

- **Autoscaling on CPU** misread waiting as idleness → removed capacity during the crisis.
- **Health checks** marked instances unhealthy because they couldn't reach backends; automation replaced them, and responders' SSH sessions ended when their instances were deprovisioned.
- **Recovery machinery overloaded**: provision-service had never handled a scale-up this large.
- **Monitoring shared fate** with the failing network path.

## How they found it

- External monitoring paged; with dashboards down, engineers used internal consoles, CLI tools, logs and metrics backends queried directly — "nowhere near as efficient".
- Slack escalated "widespread network degradation" to AWS; AWS's internal monitoring also caught packet drops.

## What they did to fix it

1. Cleared broken instances; repaired provision-service.
2. **Disabled downscaling** to preserve capacity and allow investigation.
3. **Load balancer "panic mode"**, retries and circuit breaking kept traffic flowing while many health checks failed (topic 29).
4. AWS **manually increased TGW capacity**; network normal by 10:40 AM.

## Permanent fix (as stated by Slack)

| Action | Pattern it addresses |
|---|---|
| AWS reviewing TGW scaling algorithms for large packet-per-second increases | Provider scaling |
| Slack to **request preemptive TGW upscaling** at the end of the next holiday season | Known traffic patterns |
| Run dashboard services **in the same VPC as their database** to remove the TGW dependency | Monitoring shared fate |
| **Regularly load test provision-service** | Recovery tooling at scale |
| Re-evaluate **health-checking and autoscaling** configurations so they don't overload provision-service | Autoscaling feedback loops |

## In my stack

| Same risk in my tools | How I'd prevent it |
|---|---|
| HPA/ASG scaling on CPU for I/O-bound services | Scale on request rate, concurrency or latency; protect against scale-down during incidents ([SD 12](../../System-Design/notes/12-autoscaling.md), [K8s 48](../../CKA-Certification-Course-2025/notes/48-metrics-server-and-hpa.md)) |
| Provisioning pipeline (Terraform, cluster autoscaler, bootstrap scripts) tested only for small scale-ups | Load-test big scale-ups; check `ulimit -n` and API quotas of the provisioning tools (topics 14, 35) |
| Known traffic events (Monday mornings, sales, holidays) | Pre-scale and ask providers to pre-warm (load balancers, gateways) |
| Monitoring path through the same network hub | Put monitoring close to its data and on independent paths (topic 44) |
| Deep health checks during network trouble | LB panic/fail-open settings (topic 29) |

## Follow-up questions

1. **Q: What was the real root cause?**
   A: A Transit Gateway that didn't scale fast enough for the post-holiday traffic pattern caused packet loss. Slack's impact was amplified by CPU-based autoscaling that removed capacity, a provisioning service that couldn't handle a huge scale-up, and monitoring that depended on the same network path.

2. **Q: How was it detected, and why was diagnosis hard?**
   A: External monitoring paged Slack. Dashboards and alerting were down because they depended on the TGW, so engineers had to query systems directly.

3. **Q: What was checked first?**
   A: Recent changes (rolled back, not the cause), then network connectivity — leading to escalation to AWS.

4. **Q: How did they stop the impact?**
   A: Repaired provisioning, disabled downscaling, used LB panic mode and circuit breaking, and AWS increased TGW capacity.

5. **Q: What changed permanently?**
   A: TGW pre-scaling requests, AWS reviewing TGW scaling, dashboards moved next to their database, load testing of provisioning, and autoscaling/health-check review.

6. **Q: How would you confirm the fix?**
   A: A load test of provision-service at emergency scale; a game day where the TGW path is degraded and dashboards stay up.

7. **Q: What if the provider couldn't scale the gateway quickly?**
   A: Reduce traffic through it: shed non-critical features, route around it where possible (VPC peering for critical paths), and keep enough warm capacity that you don't need to provision during the event.

8. **Q: How would you prevent this class of incident?**
   A: Pre-scale for known events, autoscale on the right signals, test recovery tools at scale, and keep monitoring independent.

9. **Q: Why did autoscaling scale down during an overload?**
   A: The web tier was waiting on network I/O, so CPU dropped. A CPU-based policy saw "idle" servers and removed them, even though users were suffering.

10. **Q: What if this happened during a deploy?**
    A: A deploy would replace instances exactly when provisioning is fragile, adding cold instances and more load on provisioning. Freeze deploys during infrastructure incidents.
